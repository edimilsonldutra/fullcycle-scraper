## Resumo da aula

O tipo de software continua sendo um critério inicial para mapear skills, como já estabelecido anteriormente, mas aqui o ponto novo é usá-lo como base para especializações mais concretas. Quando um projeto é back-end, front-end, mobile ou full-stack, cada categoria impõe conhecimentos recorrentes que podem virar skills próprias do contexto da empresa ou do produto. Isso significa que nem toda skill precisa existir previamente no ecossistema: muitas surgem da necessidade real do projeto. A utilidade prática desse mapeamento é reduzir erro da IA ao transformar expectativas implícitas da equipe em instruções especializadas.

Skills orientadas à linguagem cobrem problemas profundos demais para caber apenas em guidelines gerais. Boas práticas de Python ou TypeScript podem ficar em uma guideline, mas tópicos como otimização de performance em Python ou advanced types em TypeScript exigem instruções mais específicas, acionadas quando a tarefa realmente pede esse nível de detalhe. Essa separação evita inflar instruções genéricas com conteúdo altamente especializado. O resultado é uma IA mais precisa em tarefas técnicas de linguagem sem carregar contexto desnecessário o tempo todo.

Frameworks adicionam convenções, estruturas e decisões que não são resolvidas apenas por conhecer a linguagem base. Em Django, por exemplo, entram organização de pastas, localização de templates, modelagem, APIs e recursos administrativos; em React com Vercel ou em Spring Boot, surgem padrões próprios de uso e integração. Uma skill orientada a framework encapsula esse conhecimento operacional e reduz a necessidade de a IA improvisar ou buscar documentação externa. Isso melhora consistência arquitetural e acelera tarefas que dependem de convenções específicas do stack.

Quando a IA começa a fazer fetching na web para responder a uma solicitação técnica recorrente, isso costuma indicar falta de contexto especializado no projeto. Se a necessidade for relevante e repetitiva, vale verificar se já existe uma skill pronta ou se faz sentido criar uma. A vantagem é substituir buscas externas, páginas longas e contexto disperso por instruções organizadas e diretamente utilizáveis. Esse padrão também reduz custo de tokens e tende a tornar a execução mais estável.

Ferramentas do fluxo de desenvolvimento também podem ser encapsuladas como skills. GitHub Actions é um bom exemplo: embora a IA consiga gerar workflows genericamente, uma skill pode concentrar templates e decisões para cenários como CI, CD, push, Docker ou automação de code review. Isso transforma conhecimento operacional de tooling em um ativo reutilizável do projeto. Em vez de depender de geração ad hoc a cada pedido, a IA passa a operar com padrões mais previsíveis.

Playwright pode ser tratado como uma skill orientada a ferramenta quando o objetivo é apoiar navegação, automação e tarefas ligadas ao front-end durante o desenvolvimento. Ao concentrar instruções específicas de uso em uma skill, a IA depende menos de consultas externas e pode até reduzir o uso de servidores MCP associados à ferramenta. A consequência prática é economia adicional de tokens e menor dispersão de contexto. Retomando a lógica de carregamento sob demanda já vista antes, a skill entra apenas quando a tarefa realmente envolve Playwright.
